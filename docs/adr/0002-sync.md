# ADR-0002: Offline-first sync with client ids, last-writer-wins and a server change counter

- **Status:** Accepted
- **Date:** 2026-11-04
- **Supersedes:** none
- **Author:** founding agent (claude)

## Context

The iPhone must record a payment with no signal (the Apple Pay automation runs wherever the payment happens) and sync later. The web edits the same data while online. There is one person per instance, so concurrent edits of the same row are rare, but an offline iPhone can push an old edit hours later. Data volume is small (thousands of rows per year). Applies to: accounts, categories and transactions.

## Options

1. **Client ids, client `updated_at` with last-writer-wins per row, tombstones, server `seq` counter:** devices push dirty rows, then pull rows with `seq > since`. Simple, works over plain HTTP and SQL on both SQLite and D1.
2. **CRDTs (for example Automerge):** field level merges, but heavy libraries in Swift and JS, opaque storage, and export gets harder.
3. **CloudKit for the iPhone and a separate sync to the server:** Apple specific, two sources of truth, no web on Android.
4. **Server as the only writer (online only):** loses payments made without signal, which the PRD forbids.

## Decision

Option 1:

- Every row has a client generated id (UUID), `updated_at` (client clock, ms), `deleted` (tombstone) and `seq` (assigned by the server on each accepted write from a single counter in `meta`).
- `POST /api/sync {changes}` validates every row, then upserts with `WHERE excluded.updated_at > current.updated_at` in one transaction. The response returns the server's current version of every pushed row, so a device whose edit lost adopts the winner immediately.
- `GET /api/sync?since=N` returns every row with `seq > N` and the new `seq`; transactions are paged (`more: true`).
- The iPhone stores rows locally with a `dirty` flag. It pushes dirty rows, then pulls. A pulled row replaces the local one unless the local row is dirty and newer. A row edited again while its push was in flight stays dirty.
- Deletion is a tombstone with personal fields cleared, so deletions reach every device and deleted content does not linger on the server.

## Consequences

- One code path for the web and the iPhone. The web is a thin online client of the same API.
- Clock skew between devices can make an older edit win. Accepted for one person; `updated_at` more than 24 h in the future is rejected.
- Merges are per row, not per field: editing the note on the web and the category on the iPhone while offline keeps only the later row. Accepted for v1.
- Tombstones are kept forever (tiny). Export ignores them.
- Self-hosters get the same behavior; nothing depends on a provider.
